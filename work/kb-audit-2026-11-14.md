### 0.4 什么时候算「优化值得继续」

先测基线，再做 6 件，然后看三个数：

1. **引用可核验率**（答案里的引用能否支持结论，300 题 + 人工抽 10%）；
2. **索引期可用性**（一次全量索引期间的锁错次数 / `None` 次数，目标 0）；
3. **评测集上的召回与拒答正确率**。

三项都改善 → 再谈 BM25 / 联邦 / 面板；有一项没动 → 停下来查原因，不要继续加功能。

## 2. 本次实测纠正的事实与新增发现

### 2.1 「insights 自带 source_ref，零标注派生 300 题」不成立

- `insights` 表结构与 `source_ref` **无关**：字段是 id/title/observation/connection/hypothesis/potential_value/confidence/status/…，**没有 source_ref 列**。
- 有来源的是 `nodes`（5299 条全部有 `source_ref`，指向 `kb_para/.kb_para/inbox/raw/asr-*.txt`，469 个不同文件）；insights 通过 `insight_sources` 关联 nodes，但**只有 68/121 条 insights 有来源**。
- 这些 asr 副本与 GraphMind 文档**不能直接按内容对齐**：469 个 source_ref 里 3 个文件已不存在，其余 466 个只有 **37 个（7.9%）** 的内容 md5 命中 GraphMind `doc_status.content_hash`（索引收敛后重算；09:0x 索引期是 29/469 = 6%）；按 md5 能对上 `~/姜胡说/asr/*.txt` 的有 337 个（72%），但那些文件与 GraphMind 输入又各是一版文本（标点/繁简不同）。
- 结论：**没有现成的「问题 + 标准文档」对**。评测集要另起一条低成本路线（§4.4），成本按 **1 天** 计，比审核的 0.5–1 天上限略高。

### 2.2 75 条 `failed` 是重复拦截，但错误文案在骗监控

- 75 条记录（09:04 快照时 40 条，收敛前又累积 35 条）全部落在 `dup-*` 键下，`metadata.is_duplicate=true`、`duplicate_kind=filename`，`error_msg` 写「File name already exists.」。
- 它们对应 37 个文件名：36 个是与已入库文档**逐字节相同**的副本（共 36 组，每组 1 个副本、1 个 processed 代表），1 个是同一文件被反复喂入（其原 processed 记录被清成空壳，§2.5）。每个名字累积 2–3 条 dup：36×2 + 1×3 = 75 条。
- 抽查一对：`7691283132451966250.txt` 与 `20260930_口播的病根…txt` 内容 **md5 完全相同**（e1c6122f…，均 6619 字节）——是同一视频被两种命名（aweme_id / 日期标题）各喂了一次，去重生效。
- 但 LightRAG 的文案把「内容重复」写成「文件名重复」（实际是 doc_id＝内容 md5 相同 → 撞键），且 `status=failed`：按状态统计会把 75 条当失败；而且**每轮重扫都会给同一文件再记一条**，记录数随重试膨胀（938 个输入文件 → 977 条记录）。**修正口径**：统计重复看 `metadata.is_duplicate`，不看 `status=failed`。
- 影响：按记录数算入库率 902/977 = 92.3%，按唯一内容算是 901/902 已入库——直接拿 status 统计会低估约 8 个百分点；这也是「先别急着扩容、先把账对上」的理由。

### 2.3 9 个 AI 主题摘要 md 混在姜胡说语料里（引用可信度风险）

- `data/jianghushu-methodology_b0607c/input/` 里有 9 个 `.md`：`01-个人成长` … `09-其他`，内容形如「视频数：180 个（占总 33%）／核心：思维 + 习惯 + 心法」——是**AI 汇总稿**，不是逐字稿。
- 它们被当成普通文档索引（doc_status 里 `.md` 9 条），会和原片一起被检索。后果：问「姜胡说怎么看 X」时，答案可能引自他的**摘要**而非原话，而接口现在连 references 都不返回，用户无法分辨。
- 处理：不删也行，但必须标 `source_type=digest` 并在展示/引用时区分；这条并入 §4.5 的元数据回填，**不额外加预算**；若确认是误放，直接移出 input 并单独建 dataset（0.1h）。

### 2.4 附带一条：`/api/datasets` 不是「索引期才慢」

v1 写「25–30s 超时」；今天 09:10 实测 `GET /api/datasets` **45s 未返回（curl http=000）**。索引 12:02 收敛后复测：**27.6s / 29.8s 两次，http 200**——慢是接口本身（大概率每次都要遍历各库 rag_storage 统计），索引只是把它从 ~28s 放大到 >45s。前端/自动化仍会把「索引中」误判成「服务挂了」——这是第 2 件（锁补丁）之外的独立症状，先记录，不单列任务。

### 2.5 收敛后发现：2 条「空壳 processed」记录（各库 1 条）

- 两个库各有 1 条 `processed` 记录的 `content_length=0`、`chunks_count=0`，且没有 `content_hash`：
  - 姜胡说 `20200602_推荐大家参照以下几条线思考：种子用户 势能 裂变.txt`（输入文件 1588B；记录 `doc-5576f353…`，created 11-13 14:05、updated 11-13 18:04）；
  - 李公子 `20230622_地域优势，.txt`（输入 5038B；记录 `doc-3d2dc4b5…`）。
- 这两个文件名下另有 2–3 条 `dup-*` failed 记录，`content_length` 分别是 567 / 1709 字（正文其实在 dup 记录里）；但 processed 记录本身是空的，kv 与 vdb 都没有这对 doc_id 的 chunk（实测各 0 条）。
- 结论：**这 2 篇内容实际不在索引里**，状态却写 `processed`——按状态统计会把它们算成功。与 §2.2 同源：重复插入/一致性检查会把原记录清成空壳（日志只显示 `Preserving failed document entries`，机制未定位）。
- 影响：内容覆盖率 901/902（姜胡说）、369/370（李公子），不是 100%。
- **补数据的正确做法（12:18 按 `pipeline.py` + `indexing_service.py` 复核，修正了本稿初版「改名重喂」的建议）**：
  - 进图谱只能走索引管线（LLM 抽取 → 合并图 + 向量），没有旁路；但只需 **这 2 篇的增量索引**，不必全量重建——扫描先按 `data/<ds>/.indexed_files.json`（filename→sha256）再按 doc_status basename 跳过，其余 936 篇是秒级 skip。
  - **只改名重喂不成立**：去重按内容派生的 `doc_id` 撞键（`pipeline.py` 的 `filter_keys` → `ignored_ids` 分支；36 组不同文件名、同内容的副本都被拦成 `duplicate_kind=filename` 就是证据），改名不改 `doc_id`，仍会被拦成 `dup-*`。
  - 可靠步骤：①停服务；②从 `kv_store_doc_status.json` 删这 2 条空壳 `doc-*` 记录（可连带其 `dup-*`）；③从 `data/<ds>/.indexed_files.json` 删这 2 个文件的条目（否则第 1 步就按 filename→sha256 跳过）；④重启后触发一次索引（只处理这 2 篇，各约 1–3 分钟，末尾 storages finalize）；⑤复核 `status=processed`、`content_length>0`、`chunks_count>0`、空壳记录为 0（processed 仍是 902，真正入库 901→902；若连 dup-* 一起删，记录总数会低于 977）。
  - 成本约 20–30 分钟，期间查询会变慢（参考 §3.4 索引期延迟）；属数据修复，不在本审计工单范围。

### 3.2 索引批次与吞吐（收敛后按日志重建）

| 数据集 | 首启 → 收敛 | 墙钟 | 收敛时状态 | 平均吞吐（墙钟口径） |

- **修正本稿 09:0x 版的一处算法错误**：原文写「12:52:28 起 20h13m 走到 803/938 ≈ 40 篇/小时」，把跨了多次重启的墙钟当成一次连续运行。日志里姜胡说共有 6 次 `INDEXING START`（12:52 / 13:31 / 14:03 / 14:05 / 14:16 / 18:03）、李公子 10 次（12:42–14:20，其中 371 篇全量首启在 12:45:32），每次重启都从头扫并跳过已索引文件。结论（全量 ≈ 一天、吞吐 ≈40 篇/小时）不受影响，但「20h13m / 803 篇」不能当单轮吞吐引用。

## 5. 两条未验证假设的实测方案

### 5.1 延迟「可压到 15s」

- 现状：索引期新问题 8–102s、收敛后同批 1.8–22.3s（n=6），重复问题 1–4s（缓存）；没有任何参数对照。

- 判据：P95 达到 15s 且引用不降 → 写进 SLO；否则 SLO 写实测值，并回头查是模型限流还是输出长度。

### 5.2 「重建 >1 小时」

- 现状：**重处理**口径已实测——姜胡说全量 11-13 12:52:26 首启 → 11-14 12:02:03 收敛，**23h10m**（含 6 次重启；末轮 762 篇 / 17h58m ≈ 42 篇/小时）。冷重建（删 index + 删 37.8MB LLM 缓存）只会更慢。

- 判据：拿到冷重建实测值后再决定备份策略（若 >24h，index 冷备从「可选」升为「建议」）。

## 7. 目标模型（长期方向，不改当下动作）

### 7.1 分层（长期）

```
raw/<creator>/<aweme_id>.txt        # 不可变原文
raw/<creator>/<aweme_id>.meta.json  # 结构化元数据
catalog.sqlite                      # 文档/版本/入库事件（唯一事实源）——现在还没有
index/                              # chunks + 向量 + 图，可重建（≈23h，按天计）
notes/ (.kb_para)                   # 提炼层，引用 doc_id#chunk
```

### 7.2 现在只加字段，不建表

- 在 `doc_status.metadata` 里加 `creator / publish_at / title / source_type / asr_model`（**不需要** `content_sha1`：`content_hash` 已是内容指纹，md5，901/902 有值）。
- 等文档过万、或需要「按时间/作者过滤」成为常态查询时，再建 `catalog.sqlite`。

### 7.3 去重规则（按当前实际行为写）

| 场景 | 现在的行为（收敛后实测） |
| --- | --- |
| 同一内容换文件名再喂 | doc_id（= 内容 md5）撞键 → 拦下，记 `dup-*` + `status=failed`（**错误文案写成「文件名重复」**，见 §2.2）；本轮 36 组副本都走这条路 |
| 同一文件名重复上传 | 同一条撞键路径；每轮重扫再记一条 dup（同一文件最多见到 3 条），并且可能把原来那条 processed 记录清成空壳（§2.5，机制未定位） |
| ASR 重跑、内容变了 | 新内容 → 新 doc_id → 新记录（无版本概念，旧记录仍在） |
| 删除 | 只删 input 文件，向量/图未清（§4.7） |

### 7.4 检索流水线（参数待 A/B）

```
query → 规则路由（名字/关键词 → dataset + mode）→ 召回（向量 top50 ∥ 图邻域 top20）
      → 去重（同一观点反复讲，8 条可能全是复述）→ 可选重排（gte-rerank-v2）
      → 打包（chunk_top_k=12、≤8k token）→ 生成（≤700 token、流式、强制引用）
      → 记录 query_log；无命中 → 明确拒答
```

- 路由映射：查原话走 `naive`（`local` 是实体中心）；方法论/综合走 `mix`；不要为每次查询加一次意图分类 LLM 调用。
- 重排用 DashScope `gte-rerank-v2`（约 10 行、+0.2–0.5s），不用本地 `bge-reranker`（CPU 20 条×900 字 >10s）。
- 不重切 chunk：63% 文档已是单块（568/902，12:04 实测；中位 894 字），重切会作废现图、且全量重抽要按天计。
