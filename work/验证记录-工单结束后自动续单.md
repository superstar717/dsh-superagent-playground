## 1. 结论一句话

平台**本来就会**在 ended 工单收到人的新消息时自动「续单」（同一 Mandate 下新建 Assignment，无需人工重发）；本单修的是它为什么看起来被挡住：
① 续单被当成普通新任务排队，没用「人的消息」保留槽位（本次 12:10→12:24 延迟 13.4 分钟）；
② 工单结束时被释放给 Eval 的未读消息仍留在 worker Session 收件箱，继续起 turn，而 turn 里的工具已随工单结束收回，于是出现一串 `Ticket ended; new work needs a new authorized ticket`。

## 6. 设计取舍：为什么没有「新开一张 ticket id」

用户原话是「工单被 ended 挡住需新授权单——可做成自动开单机制」。落地时核对了现有机制与约束：

1. 平台对「ended 工单 + 人的消息」的既有语义就是**同一 Mandate 下续单**（`Tickets.wake`；文档 002/003 明确「a human's message there resumes the ticket under the same mandate」）。人的消息本身就是继续处理的授权依据，无需重新评估。
2. 若真的新建一张 ticket：`Tickets.create` 会重新跑 prepare 命令、按新 short name 建新 worktree/分支；进行中的工作区留在旧目录，且 GitHub PR 绑定按分支末段 = 旧 ticket short name，新 ticket 接不上。对「交付后追问/继续做」这类高频场景是倒退。
3. 若消息超出旧工单范围，现有 hand-back → Eval → 新 ticket 路径仍然可用（worker 先续单、判断不属于本单后 handback）。

因此本单修的是「自动续单要真的立即、干净地跑起来」，而不是新增 duplicate ticket。若决策者确实要「每条 ended 后的消息都新建 ticket id」，需要另行设计（保留同一 worktree/分支绑定、订阅归属如何从旧 ticket 转走），不在本单范围。
