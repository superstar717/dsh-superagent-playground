# 验证记录：新任务抢占在跑任务的编排问题（工单 999b7b316471）

## 结论一句话

同 work 线程新任务「挤掉」在跑任务的直接机制是：编排层把 attach 到在跑 ticket 的新 Input 用
`steer`（next-step）投进正在跑 turn 的 worker，worker 在下一个 step 立即看到新请求并转向，
在跑任务被中途弃掉。修复 = Input 一律改走 `queue`（next-turn，turn 边界投递），
辅以 worker/dispatch 提示词同步收紧。

路由侧：三条 trigger 都是**新顶层线程**消息，dispatch.md 规则 7 的「refers to the change just made
and exactly one ticket fits」分支允许了 attach（题材确实与 fa77fa33 在跑的 sph 实测同源）——规则本身
留了把**新任务**attach 到在跑 ticket 的口子。

投递侧（bug 本体）：`src/executor/dsh.ts` `deliverInput` 对所有 Input 无条件 `prompt(..., 'steer')`；
dsh core `agent.steer` 把消息放进 next-step，正在跑的 turn 在下一步立即消费它，且
`turn()` 的循环（`if (turnEnds && inbox.nextStep.length===0) break`）会因 steer 消息**不结束 turn**，
模型据此转向新请求、旧任务无 checkpoint、无报告地中断。

## 修复内容（~/dsh-superagent-prototype，commit 见该仓库）

1. `src/executor/dsh.ts` `deliverInput`：`'steer'` → `'queue'`（dsh-agent `followup`，next-turn）。
   - 在跑 turn：消息在 inbox 等 turn 结束，新 turn 才看到 → 旧任务必然先完成/报告，抢占机械上不可能；
   - 空闲 worker：followup 立即唤起新 turn，与原 steer-空闲路径行为一致（无延迟回归）；
   - 背靠背 turn：driver 在同一 activity 内接续，`agent/status` 不闪 idle，与原 turn 延续等价；
   - 与 `launch()` 已有的 `'queue'`、`resumeAfter` 的 `'queue'` 一致；幂等/去重/`live()` 守卫全部不变。
2. `prompts/worker.md`：写明「Input 只在 turn 边界到达，先完成并报告在跑任务再接新请求」。
3. `prompts/dispatch.md`：attach 规则收紧——题材相同但**开启新工作**（重测/扩展/重做）的消息按新请求
   accept，不 attach 到在跑 ticket（进度问询类仍可 attach）。
4. `docs/007-architecture.md`：Session 投递语义段落同步。
5. `tests/runtime-concurrency.spec.ts`：`failing()` 辅助从拦截 `agent.steer` 改为拦截 `agent.followup`。

## 遗留与边界

- 人工直接在 worker Session 窗口打字（src=user）仍为 DSH core 的交互路径，不受本修复影响（这是人工显式接管，非编排抢占）。
- 「两个话题的更新发进同一飞书线程」属 worker 外发投递卫生问题，worker 已在会话中自纠（分线程投递）；
  提示词层已有 answer_to 规则约束，未在本工单扩大范围。
- 历史在跑的长 ticket（如 fa77fa33 一个 ticket 累积 9 个 assignment/100+ inputs）的拆分属路由策略话题，
  本修复降低其危害（attach 消息排队而非抢占），不改变 ticket 生命周期语义。
