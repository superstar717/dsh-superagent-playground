# 项目复盘 — 图谱问答误答与「交给 superagent」改造（工单 c568a58a9d7e）

复盘时间：2026-11-13 18:50（Asia/Shanghai）
评价标准：**单一主处理方 + 可追溯 + 不丢能力**。按此标准，问题「能不能只让一个系统负责回答」比
「哪条答案更快」优先；本复盘只记录事实、取舍与可迁移的教训。

## 一、最终事实

- **现象**：飞书群同一条 @机器人 消息出现了两条答复——superagent 工单的接单回执与最终结果（正确），
  以及旁挂 kb-responder 的「图谱问答」答复（GraphMind 无联网能力，答不了调研）。用户随即质疑
  「为什么图谱问答，这应该交给 superagent 处理」。
- **根因（旧版实测复现）**：
  1. `is_question` 用 `"?" in text` 判定问句，链接查询串 `?utm_psn=` 让调研类请求通过了问句判定
     （正文里根本没有问号）；
  2. `thread_has_prior_bot_reply` 只扫「当前消息之前」的回复，且根消息（thread_position=-1）第一条
     就 `break`，检测不到 superagent 在同一线程的回执；
  3. `WORK_RE` 不含调研/研究/评估/核实/整理等祈使动词，即使修好第 1 条也没有「留给工单」的保护；
  4. 两个进程共用同一飞书 app、无「谁先接管」约定，回复也没有来源标记，群里看不出归属。
- **落地**：kb-responder 改为 **superagent 优先 + 图谱兜底**（60s 优先窗口；线程已有任何机器人消息
  即不插话；调研/工单动词永不接；兜底回复带「图谱问答·兜底」标记；GraphMind 返回 `None` 按失败处理）。
  工单侧新增 skill `jianghushu-graph-qa` 与 `~/.dsh/AGENTS.md` §十三，worker 用 GraphMind 查证后
  带 `[图谱检索]` 依据作答。
- **验证**：旧版三缺陷实测复现；新版分类 9 例、原消息注入、真实线程守卫、优先窗口、线上重启、
  一条工单型真实新消息（被正确忽略且 superagent 已接单）全部通过；图谱检索链路实跑 24.2s
  返回 899 字真实答案。细节见 [work/DEPLOY-NOTES.md](DEPLOY-NOTES.md) §6。
- **规模**：改 1 个旁挂脚本（约 +80/−30 行）+ 1 个新 skill + 1 节全局规则；线上 launchd 重启 2 次，
  一次新消息实测，无中断、无回滚。
- **遗留（如实）**：GraphMind 的 jianghushu 数据集在增量建索引期间 `/search` 返回 `"None"`
  （LightRAG 存储锁 `bound to a different event loop`，既有缺陷）；worker 暂无 `kg_*` 原生工具；
  兜底与工单存在窗口外双答的理论可能。

## 二、做得对的

1. **先查事实再改代码**：用 Feishu API 的 `sender.id` 确认两条答复来自同一 app
   （`cli_a905d6acf0f89cbb`），排除了「另一个 bot/旧网关」的猜测，避免改错系统。
2. **复现优先**：把旧版两个关键函数单独跑出 `True`/`False`，修复后用同一组输入对照，不靠日志猜。
3. **选「主处理方 + 兜底」而不是删功能**：既满足「交给 superagent」，又保留图谱能力；兜底回复
   明确标记归属，可观测、可回滚。
4. **把「交给 superagent」做完整**：不只堵住旁挂，还给工单 worker 补了查图谱的能力（skill + 规则 +
   实测可用的 REST 路径），否则「交给 superagent」只是把问题藏起来。
5. **顺手加固上游异常**：GraphMind 返回字符串 `"None"` 时按失败处理，避免把 `None` 当答案发群。

## 三、犯过的错 / 差点踩的坑

1. 一开始怀疑 openclaw 旧网关或另一个 bot，绕了约十几分钟；实际一条消息 mget + `sender.id` 就能
   定性为「同一 app 两个处理方」。
2. 线程守卫第一版方向错了（想只改判定顺序），实测才发现根消息在 asc 列表里就是第一条，
   必须改语义（扫整条线程、任一条机器人消息即接管）。
3. 图谱检索首次 e2e 拿到 `"answer":"None"`，若无空值加固，兜底会把 `None` 发进群。
4. **文档里直接引用了飞书原文、消息 id 与 chat id**，而本仓库是公开仓库——私域内容不应进 GitHub；
   本轮已把这些引用改为行为描述，并压缩提交历史清理。

## 四、如果重来会怎么做

- 第一步先拉「同一条消息的所有答复 + sender app id」时间线，再谈代码；
- 遇到「两个进程竞争同一消息」直接用「主处理方 + 兜底 + 来源标记」模型，不做逐条补丁；
- 改任何自动回答逻辑前，先把旧版判定函数做成可复现用例（这次做到，省了大量猜测）；
- 写公开仓库文档时一律用事件描述代替聊天原文与 id（本轮教训，见第三节第 4 条）。

## 五、仍未解决 / 后续建议

1. **GraphMind 存储锁跨事件循环**：索引跑完后重启 `com.huweixing.graphmind` 可恢复 jianghushu
   数据集查询；根治需修 graphmind-replica（索引任务与查询的事件循环/锁用法），建议另立工单。
2. **worker 的 `kg_*` 原生工具**：superagent `WORK_TOOLS` 白名单未含，skill 现走同一 REST 接口；
   如需原生工具，加白名单需宿主重启，建议另立工单。
3. **窗口外双答**：20s 轮询 + 60s 优先窗口 + `create_time` 分钟精度，理论仍可能双答；如要消除，
   需要 kb-responder 读取 superagent 的「已接单」状态（例如共享 outbox 或状态文件），另立工单。
4. GraphMind 的 `answer:"None"` 建议在服务侧也显式返回错误码，而不是字符串 `"None"`。
