复盘时间：2026-11-13 21:50（Asia/Shanghai）
评价标准：**该拦时真拦、不误伤、免重启生效、可回归**。按此标准，机制放哪个 hook/入口、是否硬拒
都服从「真实会话里能不能起作用」；本复盘只记录事实、取舍与可迁移的教训。

## 一、最终事实

- **交付**
  - P1：`~/.dsh/bin/gh-auth-safe.sh`（设备授权单点入口：mkdir 串行锁、等待在跑流程、不杀进程、
    授权后验本机 + GitHub 侧 scopes）+ `gate_pretool.sh` v4（已加载 PreToolUse，现读生效；
    拒绝直接 `gh auth login/refresh` 与针对 gh auth 的 `pkill/kill/killall`）。
  - P2：`~/.local/bin/gh-agent`（gh 入口，`gh pr create` 前调预检）+ `gh-pr-overlap-precheck.sh`
    （open PR 同文件重叠警告，不硬拒；`DSH_PR_OVERLAP_OK=1` 显式豁免）。
  - 回归：3 个自测（18+6+9=33 项）与 CI 工作流；仓库副本在 `work/scripts/`。
- **关键事实**：hook 子进程的 Security 会话不可用（`security list-keychains` 报 Module Directory
  Service error；gh 401 tokenSource default），因此 P2 不能放在 PreToolUse/PostToolUse 里做
  `gh pr list`——改为 `gh` 入口 gh-agent（与命令同环境），警告随 stderr 在 PR 创建前出现。
- **验证**：真实会话中 4 类危险命令被拦、wrapper 放行并校验通过、含重叠文件的分支上
  `gh pr create --help` 先出警告、豁免生效；脚本级 33/33；仓库副本经 `SELFTEST_BIN` 同样通过。
- **规模**：新增 2 个脚本 + 改 2 个（gate v3→v4、gh-agent 2 行→带预检）+ 3 个自测 + 1 个 CI
  工作流；本机与仓库副本同步；未重启宿主、未改 hooks.json。
- **遗留（如实）**：`orchestrator_report` 证据门禁仍未加载（需重启 + e2e）；`gh-agent` 只覆盖
  agent 常规 gh 入口；本机 keychain 在并发 gh 下会间歇失败（wrapper 已重试 + API 兜底，P2 失败
  静默跳过）；P2 对 `--help`/`--dry-run` 也会跑（约 2s，无副作用）。

## 二、做得对的

1. **先在真实会话验证，不迷信脚本级测试**：PreToolUse/PostToolUse 方案脚本自测全过，真实 e2e
   才发现 hook 进程 401；没有把「自测通过」当成「机制生效」（E44/E127 纪律）。
2. **用最小诊断定位环境差异**：在 hook 里只加临时诊断（gh 版本、`security list-keychains`、
   env、anon API），拿证据后立刻移除；没有在错误方向继续堆代码。
3. **失败分类后换路径**：判断为「hook 进程环境读不到钥匙串」而非「gh 坏了」，把 P2 移到同环境的
   gh 入口，既解决问题又让警告出现在 PR 创建之前（比 PostToolUse 更早）。
4. **P1 保留在已加载 hook**：满足「免重启生效」；串行锁 + 等待 + 双端校验，且门禁拒绝的是真正
   危险的四个模式，放行普通 gh 用法。
5. **回归可跑**：三个自测都用 fake gh/临时仓库，CI 不需要真实 token；不把账号密钥写进测试。

## 三、犯过的错 / 差点踩的坑

1. 第一版把 P2 放在 PreToolUse（写待提醒 → PostToolUse 注入），在 hook 401 上花了约 40 分钟
   排查；若先做 10 行「hook 里 gh 能不能用」探测（`gh auth status` + `security list-keychains`），
   可早 20 分钟转向。
2. 调试时临时给 `gate_pretool.sh` 加过 `_diag`、给 `lessons_intercept.sh` 加过测试块/env dump，
   其中测试块一度随真实命令触发了假的注入（PR-OVERLAP-TEST-CONTEXT）——临时调试代码必须
   带清晰标记、用完即删，并在提交前 grep 确认。
3. 自测里用 `TMP` 前缀 `gh-auth-safe.*` 作慢进程路径，被 wrapper 的 `grep -v gh-auth-safe` 过滤，
   导致「等待在跑流程」测试假失败；同时也说明过滤条件过宽，已改为只按 pgrep 匹配。
4. 起初 `verify` 没考虑 keychain 瞬时失败（实测 21:22 出现过一次 `gh auth status` 报 invalid），
   会对正常会话误报 rc=3；后加 3 次重试 + API 兜底。

## 四、如果重来会怎么做

- 任何「hook 内要访问网络/凭证」的设计，先跑一个 10 行兼容性探测（gh 能否用、钥匙串能否读），
  再决定放 hook 还是放命令入口。
- P1/P2 这类安全机制先明确「拦什么/放什么/失败怎么办」三张表，再写规则；失败路径一律不阻断
  （除明确危险命令）。
- 调试注入代码用独立文件 + 显式前缀，并纳入「提交前 grep 清理」清单。

## 五、仍未解决 / 后续建议

1. **`orchestrator_report` 证据门禁未加载**（E127 同类）：需要重启宿主，并在重启后做一次
   「带 human_action 且无排障证据」的真实报告 e2e 才算防线；本工单为避免中断在跑会话未重启。
2. **钥匙串并发失败**：多 worker 同时跑 gh 时 `gh auth status`/`gh pr list` 会间歇 401/timeout；
   wrapper 已缓解，根治需宿主/gh 层串行或改用 `GH_TOKEN` 注入（安全权衡另议）。
3. **P2 覆盖面**：直接调用真实 gh 二进制、非 agent 环境的 `gh pr create` 不经过 gh-agent；
   如要全量覆盖，可考虑在团队级 gh 包装或 CI 层再加一道。
4. **P2 预检成本**：每次 `gh pr create` 多 ~2s（`gh pr list`）；如觉得慢可加短 TTL 缓存，但会
   牺牲新开 PR 的即时性。
