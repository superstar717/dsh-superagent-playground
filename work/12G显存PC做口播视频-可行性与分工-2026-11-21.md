# 12G 显存 PC 做口播视频：可行性与分工

> 日期：2026-11-21（Asia/Shanghai）｜工单 `39a55aaf…`｜来源：飞书群提问「我们有一台 12G 显存的 PC 端电脑，关于剪辑口播视频，是不是可以在 PC 电脑上做呢」
> 关联口径：2026-11-17 同群已就「Harness + Pixelle-Video」给过 12–16G / 24G / 云端的结论；本文与之一致，不另立叙事。
> 补充（2026-11-21 11:34 同线程追问）：目录怎么规划、信息何时同步、频次多少——见第 5 节。

## 0. 直接回答

**能，而且 12G 对口播剪辑是宽裕的。** 口播视频的主链——剪辑、字幕、配音、编码——只吃 6–8G 显存；12G 的 PC 不但够，还能把现在只能跑在 CPU 上的配音克隆（本机实测 100–165 秒/句）降到秒级。

**唯一超出 12G 的是「本地文生视频」**：官方口径 24G 起（Wan2.2 TI2V-5B）、14G 起（HunyuanVideo 1.5 720p），12G 只能跑量化/offload 的草稿档。所以那一步继续走模板或云端，不要指望 12G 本地批量出 AI 画面。

**推荐分工一句话**：PC 当 GPU 计算面（配音克隆、字幕、唇形/超分、编码导出），Mac 保留编排面（选题、文案、知识库、素材抓取、已验证的模板出片、质检与飞书交付），云端只兜底生成式画面。

## 1. 先按「口播视频有哪几种做法」拆开

同一句「剪辑口播视频」其实有四种形态，12G 的够用度完全不同。先对号入座，再谈配置。

| 形态 | 典型做法 | 12G 结论 | 说明 |
|---|---|---|---|
| A. 文字动效 + 克隆配音（**当前默认路线**） | MotionGit 模板 + CosyVoice2 克隆音 | **够，甚至过剩** | 模板渲染吃 CPU/编码，几乎不吃显存；配音克隆 6–8G |
| B. 真人实拍 + 剪辑 | 相机/手机录口播 → 剪映/达芬奇 剪 + 字幕 + 调色 + NVENC 导出 | **舒适** | 1080p 多轨 8–12G；4K 时间线建议代理 |
| C. 真人形象 + 克隆音（数字人） | 一张/一段真人素材 + 唇形驱动（MuseTalk / LatentSync） | **可做，但锁 256×256** | LatentSync 1.6 的 512×512 官方要 18G，12G 不够 |
| D. AI 生成画面（文生视频/图生视频） | Wan2.2 / HunyuanVideo / MiniMax-H3 类 | **只够草稿** | 官方 24G/14G 起；以 12G 社区实测档为例，5 秒片段约 5–7 分钟，不适合批量 |

**所以问题的答案是分层的**：A、B 完全可以在 PC 上做且体验更好；C 可以但分辨率有上限；D 不建议把 PC 当主力，继续用模板或云端 API。

## 2. 12G 显存逐项判定（附依据与标签）

标签约定：**【官方】**=仓库 README/官方文档；**【社区】**=第三方实测或配置页；**【本机】**=本机实测；**【估算】**=按公开数据推算、未在目标机验证。

| 环节 | 工具/模型 | 显存需求 | 12G 判定 | 依据 |
|---|---|---|---|---|
| 剪辑（1080p） | 剪映专业版 | 最低 2G，推荐 6G | A 够用 | 【社区】剪映 Windows 配置要求 |
| 剪辑/调色（1080p） | 达芬奇（免费版单卡） | 8–12G | A 够用 | 【社区】厂商博客/配置汇总：1080p 最低 8G |

| 配音克隆 | CosyVoice3-0.5B | 第三方建议 8G+（官方未公布） | A 够用 | 【社区】第三方部署文档；模型 0.5B |

| 唇形 | LatentSync 1.5（256×256） | **官方最低 8G** | A 够用 | 【官方】README |
| 唇形 | LatentSync 1.6（512×512） | **官方最低 18G** | D 不够 | 【官方】README |

| 超分/补帧 | Real-ESRGAN 1080p 2× | 约 6.2G（叠加 RIFE 约 10.8G） | A 够用 | 【社区】修复类实测汇总 |
| 文生视频（草稿档） | HunyuanVideo 1.5 720p | **官方最低 14G**（开启 offload） | C 只够草稿（12G 需更强量化/offload；社区有 6G 档 Wan2GP） | 【官方】README |
| 文生视频 | Wan2.2 TI2V-5B | **官方命令（已开 offload）仍需 ≥24G**（RTX 4090） | C 只够草稿（社区 GGUF 量化可上 12G，质量/时长受限） | 【官方】README |
| 文生视频（旗舰） | Wan2.2 T2V-A14B | 官方 80G | D 不够 | 【官方】README |
| 文生视频（社区量化） | MiniMax-H3（33B 音视频联合） | 社区 12G 实测：1280×736，Turbo LoRA 4 步约 420s/5s 段，权重约 42G | C 只够草稿（单镜头可以，批量不划算） | 【社区】12G ComfyUI 指南（2026-08） |
| 本地写稿（可选） | 7B–14B 量化 LLM | 约 6–10G（14B Q4 约 9–10G）【估算】 | A/B 够用 | 本机现有云端模型更省心，不必为写稿上本地 |

**一句话读表**：把「剪辑 + 字幕 + 配音 + 可选唇形/超分」放进 12G，余量充足；把「文生视频」放进 12G，只能当草稿机。

## 3. 对照本机现有链路：哪些该搬、哪些别动

本机是 **MacBook Pro 14,3（Intel i7-7920HQ 4 核 / 16GB / 无 NVIDIA 独显）**【本机】。现有口播链路里各环节的真实开销如下：

| 环节 | 现在在哪跑 | 现在实测 | 搬到 12G PC 后的变化 | 建议 |
|---|---|---|---|---|
| 模板渲染出片 | Mac，`~/.local/motiongit-385712/make_video.sh` | 27s/1620 帧 **10–15 分钟**；`render.mjs` 以 `--disable-gpu` 启动 Chromium，逐帧 1080p60 截 JPEG 再走 ffmpeg `libx264 veryfast`【本机】 | GPU 基本不参与；快在 CPU 单核+编码。现代 12 核 PC 估计 3–6 分钟【估算】 | **一期不动**（已验证的链路，移植有成本）；日产 ≥3 条再考虑二期迁移 |
| 配音克隆 | Mac CPU，CosyVoice2-0.5B | **RTF 13–24，100–165 秒/句**；一条 27s 视频（约 10 句）要 17–27 分钟；克隆相似度 0.8624/0.8428【本机】 | GPU fp16 推到秒级/句【估算】，同一条从 ~20 分钟降到 ~1–3 分钟【估算】 | **一期优先搬**：收益最大、改动最小（同一模型、同一参考音） |
| 字幕/逐字稿 | Mac CPU，SenseVoice-small | RTF≈0.12，已够快【本机】 | 提升有限 | **留 Mac**；PC 另装 faster-whisper 只用于需要词级时间戳/英文场景 |
| 真人唇形 | Mac CPU，Wav2Lip | 96×96 重绘上限，特写糊/抖；被用户指出「不如原片顺畅」【本机复盘】 | MuseTalk（可实时）或 LatentSync 1.5（更慢但更稳）上 256×256，质量台阶式提升 | **按需**：只有必须保留真人形象时启用；按 AGENTS §16 默认仍走模板 |
| 素材抓取/入库 | Mac（dysub/视频号提取/SenseVoice 入库） | 稳定运行 | 无收益 | **不动**：知识库与抓取都在 Mac |
| 模板渲染 | Mac | 同上 | 见上 | 二期可选 |
| 质检/交付 | Mac（ffprobe/响度/抽帧/飞书） | 已机制化 | 无收益 | **不动** |

**为什么不让 PC 接管一切**：模板链依赖 bash + `uv` + Playwright + ffmpeg，在 Windows 上要么改用 PowerShell 重写，要么进 WSL2；知识库、抓取、飞书交付都在 Mac。为了「统一到一台机器」付这次移植成本，收益只有渲染提速那几分钟，不划算。**分工的边界应该是「哪个环节吃 GPU，就去 PC」，而不是「整条链搬过去」。**

**与 2026-11-17 结论的关系**：当时说「12–16G 本地文生图可行，文生视频 24G 才舒适，30 秒短片走云端约 5–9 元」。本文没有推翻它——口播的**剪辑/配音**正好落在 12G 舒适区，**生成式画面**仍然越界，继续云端。

## 4. 推荐分工（三机三层）

```
┌────────────────────────────── Mac（编排面，保留现状）──────────────────────────────┐
│ 选题/文案/知识库 · 视频号/抖音素材抓取(dysub/sph) · 模板渲染出片(make_video.sh)      │
│ 质检(ffprobe/响度/抽帧/ASR 回灌) · 飞书交付 · 工单编排                              │
└───────────────▲──────────────────────────────────────────────┬──────────────────────┘
                │ 回传：segs/*.wav + timing.json + 成片        │ 下发：script.txt + prompt.wav
                │                                              ▼
┌──────────────────────── 12G PC（GPU 计算面）────────────────────────────────────────┐
│ Windows 原生：剪映专业版 / 达芬奇（剪辑·字幕·调色·NVENC 导出）                       │
│ WSL2（CUDA 直通）：CosyVoice2/3 配音批处理 · faster-whisper · MuseTalk/LatentSync 1.5 │
│                    Real-ESRGAN/RIFE · 可选本地 LLM                                   │
└──────────────────────────────────────────────────────────────────────────────────────┘
                                  │ 只在需要生成式画面时
                                  ▼
┌──────────────── 云端（兜底）：文生视频 / 旗舰数字人，按条计费 ────────────────────────┐
└──────────────────────────────────────────────────────────────────────────────────────┘
```

### 4.1 一期（建议先做，半天配置）

1. **PC 接管配音克隆**：把 `~/.local/oral-video-tools/tts_cosyvoice2.py` 原样搬过去（同一模型、同一 10s 参考音）。CosyVoice2 在有 CUDA 的机器上会自动用 GPU；脚本里 `fp16=False`，显存紧时改 `True`。先在 10 句脚本上记录 RTF 与显存峰值。
2. **PC 接管剪辑**：剪映专业版（免费、上手快、有智能字幕与文本朗读）+ ffmpeg NVENC；4K 素材一律先做代理。
3. **PC 可选接管字幕**：faster-whisper large-v3-turbo（约 2G 显存）出词级时间戳；中文仍以 SenseVoice 为准（品牌名误识已记录，字幕只作辅助）。
4. **Mac 不动**：模板渲染、素材抓取、知识库、质检、交付。

**周期账（把收益说清楚）**：现在一条 27s 成片 = 配音 17–27 分钟 + 渲染 10–15 分钟 ≈ **30–45 分钟**；只做一期（配音上 PC、渲染留 Mac）≈ **12–18 分钟**，瓶颈变成渲染；二期把渲染也迁 PC 后 ≈ **5–8 分钟**（含人工折腾的余量按估算给）。所以一期就值得做，二期看日产条数再决定。

**约定数据流**（同一份 job 目录，谁产出谁写；完整目录、所有权与同步矩阵见第 5 节）：

```
jobs/20261121-coffee-oral/
  00-input/   script.txt  prompt_10s.wav  user.json      # Mac 写
  10-tts/     segs/*.wav  timing.json  tts.log           # PC 写
  30-render/  silent.mp4  preview.png  render.log        # 渲染方写
  40-final/   final.mp4  final.wav  subs.ass             # Mac 写
  90-meta/    status.json  events.jsonl  handoff.md      # 当前阶段写
```

传输走 PC 共享盘（Mac 挂载 `/Volumes/oral`）；PC 侧只暴露一个 CLI（输入 job 目录，输出 segs/timing），不要在两台机器上各写一套业务逻辑。

### 4.2 二期（可选）：模板渲染迁 PC

触发条件：**日产 ≥3 条、渲染稳定成为瓶颈**（现在 10–15 分钟/27s，一天 3 条就是 30–45 分钟纯等待）。

做法：在 WSL2 里跑通 `make_video.sh`（bash/uv/ffmpeg/Playwright 全套都在 Linux 侧），先跑 `selftest.py` 11 项，再用同一份 `user.json` 与 Mac 版逐帧比对 3 个时间点。**注意**：WSL2 里 NVENC 是否可用取决于驱动/容器配置（社区两种报告都有），稳妥起见编码继续用 libx264；这一期省的是 CPU 与并行，不是 GPU。

### 4.3 三期（按需）：真人唇形

只有用户明确要「保留真人形象」时才做：MuseTalk（MIT）或 LatentSync 1.5（Apache-2.0，256×256，官方 8G）。**不要**在 12G 上试 LatentSync 1.6 的 512 档（官方 18G）。按 AGENTS §16，默认路线仍是模板 + 克隆音，不做唇形。

## 5. 目录与信息同步规划（长任务随时可查）

> 目标：无论是 20 分钟的配音批处理还是 15 分钟的渲染，任何时刻都能一条命令回答三个问题：**卡在哪一步、还剩多久、下一步谁做**。

### 5.1 结论先说（2026-11-21 落地版）：PC 单副本 + Mac SSH 拉取，不用 SMB

**不建议**两台机器各存一份双向同步，也不建议依赖 SMB 挂载。实测结论（当天踩坑记录，详见 LESSONS E201/E202）：

- Mac 经 Tailscale `mount_smbfs` 挂载**会话能建立但目录 IO 全部挂死**（PC 端 NumOpens=0，请求没到服务端）；`smbutil view` 正常——控制面通、数据面死；
- 局域网直连 445 被拒（139 通，PC 端监听与防火墙均正常，根因未明）；SMB 死挂载连 `umount -f` 都卡，须 PC 端踢会话才释放；
- **SSH（administrator 公钥）全程秒回**，sftp 文件往返 1.3s，无任何死锁。

**落地架构**：

- PC 上 `D:\oral` 是 job 的**唯一副本**（已建：目录骨架 + SMB 共享 `oral` + 局域网账户 `oral` 保留给 Windows 侧/其他机器用；Mac 不走 SMB）；
- Mac 每次只拉「小状态」：`oral-fetch-status.sh` 经 SSH 把所有 `jobs/*/90-meta/status.json` 拉到本地缓存 `~/oral-cache/`（可 `--watch 15` 常驻）；
- 大文件按需走 sftp/scp（成片交付时拉回 Mac）；
- 「同步」三处不变：①建任务推输入（sftp put，立即）②阶段完成写产物（事件触发，PC 本地写）③状态心跳（PC 写 ≤10s、Mac 拉 15s）。

### 5.2 目录规范

```
oral/                                # PC: D:\oral；Mac: /Volumes/oral
├─ jobs/
│  └─ 20261121-coffee-oral/          # <YYYYMMDD>-<slug>，按日期排序
│     ├─ 00-input/                   # Mac 写：script.txt prompt_10s.wav refs/ user.json
│     ├─ 10-tts/                     # PC 写：segs/seg_01.wav… timing.json tts.log
│     ├─ 20-edit/                    # 剪辑方写：draft/（剪映草稿）或 plan.json instance/
│     ├─ 30-render/                  # 渲染方写：silent.mp4 preview.png render.log
│     ├─ 40-final/                   # Mac 写：final.mp4 final.wav subs.ass cover.png
│     └─ 90-meta/                    # 当前阶段方写：status.json events.jsonl handoff.md manifest.json
├─ queue/                            # 可选：Mac 投递、PC 消费的任务队列
├─ archive/YYYYMM/                   # 归档
└─ bin/                              # job-status 等脚本（两台机器同一份）
```

为什么编号：`ls` 的排序就是流水线顺序，一眼看出卡在第几段；清理时按段删（`30-render/` 可整段删，`00-input/` 要留）。

### 5.3 所有权：一段目录只有一个写者

| 目录/文件 | 写者 | 读者 | 说明 |
|---|---|---|---|
| `00-input/*` | Mac | PC | 建任务时一次写入；改稿=新 job |
| `10-tts/*` | PC | Mac | segs 与 timing 由 PC 产出 |
| `20-edit/*` | 剪辑方 | 双方 | 谁剪谁写，不双写 |
| `30-render/*` | 渲染方 | 双方 | 大文件；完成后落盘 |
| `40-final/*` | Mac | 双方 | 交付版本 |
| `90-meta/status.json` | 当前阶段 owner | 双方（只读） | 原子覆盖 |
| `90-meta/events.jsonl` | 任意阶段（只追加） | 双方 | 每行一个 JSON |
| `90-meta/handoff.md` | 当前阶段 owner | 人 | 一段话交接 |

规则：**同一路径绝不双向同步**；跨机器写文件一律「先写 `.tmp` 再 rename」，避免看板读到半个 JSON。

### 5.4 同步矩阵：什么时候、多久一次

| 内容 | 通道 | 方向 | 触发时机 | 频次/时延 |
|---|---|---|---|---|
| 输入（script/参考音） | sftp put（SSH） | Mac→PC | 建任务 | 立即，秒级 |
| 状态 `status.json` | SSH fetch（`oral-fetch-status.sh`） | PC→Mac | 阶段运行中 | 写侧 ≤10s；Mac 拉 15s |
| 事件 `events.jsonl` | SSH fetch | PC→Mac | 阶段切换/失败 | 随状态一起拉 |
| 日志 | `ssh tail` | PC→Mac | 排障 | 按需，不落 Mac 盘 |
| `segs/`+`timing.json` | sftp get（SSH） | PC→Mac | 10-tts 完成 | 事件触发，秒级（几 MB） |
| 预览图 | sftp get | 渲染方→Mac | 30-render 每 10% | 可选，<1MB |
| 成片 mp4 | sftp get | PC→Mac | 交付时 | 按需；<200MB 自动，>200MB 手动 |
| 元数据+成品备份 | rsync | PC→Mac/外置盘 | 每日 03:00 | 每天一次 |
| 全量归档 | rsync | →archive/NAS | 月末 | 每月一次 |

### 5.5 状态文件与心跳（长任务的「遥测」）

`status.json`（原子覆盖，≤10s 一次）：

```json
{
  "job": "20261121-coffee-oral",
  "stage": "10-tts",
  "step": "sentence 7/12",
  "percent": 58,
  "state": "running",
  "owner": "pc",
  "host": "DESKTOP-XXX",
  "pid": 12345,
  "started_at": "2026-11-21T11:40:02+08:00",
  "updated_at": "2026-11-21T11:42:10+08:00",
  "eta_s": 240,
  "artifact": "segs/seg_07.wav",
  "message": "CosyVoice2 fp16, RTF 0.18",
  "next": "12 句齐后跑 join_tts_v2.py",
  "error": null
}
```

约定：

- `state` ∈ `running/done/failed/blocked`；`error` 只在 failed 时非空；
- 写侧每 ≤10s 刷新 `updated_at`；看板超过 30s（3 倍）判 `STALE`，提示「进程可能挂了 / 机器离线」；
- `events.jsonl` 只追加，阶段切换、失败、重跑各写一行；
- `handoff.md` 在阶段边界用一段话写清「做到哪、下一步、有没有坑」，人接手先看它；
- 阶段脚本里贴这几行即可（原子写）：

```python
import json, os, socket, tempfile
from datetime import datetime, timezone

def write_status(path, job, stage, owner="pc", **kw):
    data = {"job": job, "stage": stage, "state": "running", "owner": owner,
            "host": socket.gethostname(),
            "updated_at": datetime.now(timezone.utc).isoformat(timespec="seconds"), **kw}
    fd, tmp = tempfile.mkstemp(dir=os.path.dirname(path), prefix=".status-", suffix=".tmp")
    with os.fdopen(fd, "w", encoding="utf-8") as f:
        json.dump(data, f, ensure_ascii=False)
    os.replace(tmp, path)
```

### 5.7 断网、冲突、保留

## 6. 落地清单（照着做，半天）

1. **先确认卡型**：`nvidia-smi` 记录型号、显存、驱动、CUDA。同样 12G，RTX 3060 12G 带宽约 360GB/s，4070/5070 12G 约 504/672GB/s——**对 T2V/超分影响近 2 倍，对 TTS/ASR/剪辑影响很小**。型号不同，结论不变，速度预期要改。

6. **基准**：10s 参考音 + 10 句脚本跑 CosyVoice2，记录「秒/句、RTF、显存峰值」；再跑 10s 唇形片段记录同样指标。**没有基准就不要下「快了多少倍」的结论**。

## 8. 可直接转发的答复

### 8.1 关于「12G 能不能做」（原问题）

> 可以，12G 显存对口播剪辑足够：剪辑/字幕/配音/编码主链只要 6–8G，最大收益是把 CPU 上 100–165 秒/句的配音克隆降到秒级。真正超出 12G 的只有本地文生视频（官方 24G 起），那一步继续走模板或云端。建议 PC 负责 GPU 计算，Mac 保留编排、素材抓取和模板出片。

### 8.2 关于「目录与同步」（追问）

> 目录按 `jobs/<日期>-<名字>/` 分 `00-input`、`10-tts`、`20-edit`、`30-render`、`40-final`、`90-meta` 六段，一段只有一个写者，避免互相覆盖。文件不来回同步：PC 开共享盘当唯一副本，Mac 挂载读写；状态每 10 秒写一次 `status.json`，看板每 15 秒刷新、30 秒没心跳标红；大成品交付时按需拉，元数据与成品每天 03:00 备份。长任务跑到一半，一条命令就能看到「卡在哪一步、还剩多久、下一步谁做」。
